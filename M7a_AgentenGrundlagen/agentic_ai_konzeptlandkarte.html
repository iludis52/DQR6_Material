Agentic AI — Konzeptlandkarte

Systematische Taxonomie agentic-AI-Konzepte, geschichtet nach Architekturrolle. Korrigiert Unschärfen gängiger Übersichten, füllt kritische Lücken, und markiert, was tatsächlich agentisch ist — und was nicht.

GENUIN AGENTISCH HYBRID / OPTIONAL NICHT AGENTISCH ERGÄNZT = fehlt in gängigen Übersichten
01 Kernmechanik — Was macht etwas agentisch?

Die minimal notwendigen Bausteine, ohne die ein System kein Agent ist: autonome Schleife, Planung, Zustandshaltung, Werkzeugnutzung.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
Agent Loop Zyklus aus Perceive → Plan → Act → Observe → Decide(Continue|Stop). Entscheidend: Der Agent entscheidet selbst, ob er den Zyklus fortsetzt oder terminiert. Ohne autonome Terminierungsbedingung ist es kein Agent Loop, sondern eine Schleife mit Exit-Condition. Die meisten Darstellungen vergessen den Terminierungsschritt. In der Praxis sind Runaway-Loops (Agent terminiert nie) das häufigste Produktionsproblem. Gute Implementierungen haben sowohl inhaltliche Stopps (Ziel erreicht) als auch strukturelle Stopps (Max-Iterations, Timeout, Budget). AGENTISCH
Planning ERGÄNZT Der Agent zerlegt ein Ziel in Teilschritte und passt den Plan zur Laufzeit an. Unterscheide: Upfront Planning (Plan vor Ausführung) vs. Incremental Planning (Plan entsteht schrittweise) vs. Replanning (Plan wird bei Fehler/neuer Info revidiert). Kritische Lücke in den meisten Übersichten. Planning ist der Kern von Agentizität — ohne Planning ist jedes System reaktiv. Aktuelle LLMs können planen, aber schlecht revidieren: Sunk-Cost-Bias im Plan ist ein dokumentiertes Problem. AGENTISCH
State Management ERGÄNZT Konsistente Verwaltung des Agentenzustands über Schritte hinweg. Umfasst: Welche Variablen beschreiben den aktuellen Zustand? Wie werden Zustandsübergänge validiert? Welche Invarianten müssen gelten? Formal modellierbar als EFSM (Extended Finite State Machine). In LangGraph: State-Objekt + Reducer-Funktionen. Fehlendes State Management ist die häufigste Ursache für inkonsistentes Agentenverhalten. Ohne explizites State-Schema debuggt man blind. AGENTISCH
Tool Use Der Agent ruft externe Werkzeuge auf (APIs, Code-Interpreter, DBs). Unterscheide: Single-shot Tool Use (ein LLM-Call wählt ein Tool) vs. Iterative Tool Use (Agent nutzt Tool-Ergebnisse für nächste Entscheidung). Nur iterative Tool Use ist genuin agentisch. Single-shot Tool Use (z.B. Function Calling in einem Chat) ist eine LLM-Fähigkeit, kein Agentenmerkmal. Die Verwechslung der beiden ist weit verbreitet. HYBRID
02 Architekturmuster — Wie werden Agenten strukturiert?

Kompositionsmuster: Vom einfachen Chain bis zum dynamischen Multi-Agent-System. Wichtig: Nicht jedes Muster ist agentisch.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
Prompt Chain / Pipeline Lineare Kette: Output von Schritt n wird Input für Schritt n+1. Deterministische Abfolge, kein LLM entscheidet über den nächsten Schritt. Abgrenzung: Kein Agent — keine autonome Entscheidung über Kontrollfluss. In der Originalgrafik als zwei getrennte Konzepte geführt (Prompt Chaining + Agentic Pipeline). Beide beschreiben dasselbe: eine feste Sequenz. Ist die Basis vieler Systeme, aber das Gegenteil von Agentizität. NICHT AG.
ReAct Spezifisches Prompting-Schema (Yao et al. 2022): Thought → Action → Observation in expliziter Alternation. Das LLM verbalisiert sein Reasoning vor jeder Aktion. Häufig mit dem allgemeinen Konzept „Reasoning + Acting" verwechselt. ReAct ist ein konkretes Paper/Schema, keine Architekturkategorie. Modernere Ansätze (z.B. LangGraph) implementieren denselben Effekt strukturell statt über Prompt-Formatierung. AGENTISCH
Orchestrator Zentrale Instanz, die Teilaufgaben verteilt. Unterscheide: Statischer Orchestrator (fester DAG, z.B. Airflow-artig) vs. Dynamischer Orchestrator (LLM entscheidet Routing zur Laufzeit). Nur der dynamische Orchestrator ist agentisch. Die Originalgrafik trennt Orchestrator und LLM Router, aber ein dynamischer Orchestrator ist ein LLM Router. Der Unterschied liegt in der Granularität: Orchestrator verteilt Tasks, Router wählt Modelle. HYBRID
Multi-Agent System Mehrere Agenten mit eigenen Rollen, State und Tools, die über definierte Protokolle kommunizieren. Architekturvarianten: hierarchisch (Orchestrator → Subagents), peer-to-peer (Blackboard), oder marktbasiert (Auktionsmechanismen). „Gleichzeitig und koordiniert" (wie im Original) ist naiv — Concurrency erzeugt Race Conditions, State-Konflikte, Deadlocks. Produktive MAS brauchen explizite Koordinationsprotokolle. Auch: Mehr Agenten ≠ bessere Ergebnisse — Kommunikationsoverhead wächst quadratisch. AGENTISCH
Subagent / Delegation Ein Agent delegiert eine Teilaufgabe an einen spezialisierten Agenten. Kritische Fragen: Welche Informationen werden übergeben? Wie wird das Ergebnis validiert? Kann der Subagent seinerseits delegieren (rekursive Delegation)? Rekursive Delegation ist das größte Risiko: Ein Subagent, der eigene Subagents spawnt, kann exponentielle Kosten und unkontrollierbare Ausführungsbäume erzeugen. Delegation Policies (Tiefenlimit, Budget-Propagation) sind Pflicht, werden aber selten thematisiert. AGENTISCH
LLM Router Wählt pro Anfrage das passende Modell (Größe, Kosten, Latenz, Fähigkeit). Kann regelbasiert (if/else), classifier-basiert, oder selbst LLM-basiert sein. Bootstrapping-Problem bei LLM-basiertem Routing: Wer routet den Router? Praktischer Ausweg: leichtgewichtiger Classifier als Router, nicht das teuerste Modell. Funktional Teilmenge des Orchestrators — Eigenständigkeit als Konzept ist diskutabel. NICHT AG.
03 Wissen & Kontext — Woher weiß der Agent, was er weiß?

Wie der Agent auf Wissen zugreift, es speichert und an die Realität anbindet.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
Context Window Der verfügbare Tokenraum für die aktuelle Anfrage. Fungiert als Arbeitsgedächtnis: Alles, was der Agent „gleichzeitig sehen" kann. „Größer = besser" ist falsch. Empirisch: LLMs nutzen Information in der Mitte langer Kontexte schlecht (Lost-in-the-Middle). Effektive Kontextnutzung erfordert aktives Kontextmanagement (was rein, was raus, in welcher Reihenfolge). NICHT AG.
RAG Retrieval-Augmented Generation: Vor der Antwort werden relevante Dokumente aus einem externen Korpus abgerufen und in den Kontext injiziert. Varianten: naive RAG (Embed → Retrieve → Generate), Advanced RAG (+ Reranking, Query-Transformation), Agentic RAG (Agent entscheidet iterativ über Retrieval-Strategie). RAG reduziert Halluzinationen nicht automatisch — es verlagert das Problem. Der Retrieval-Schritt kann irrelevante Chunks liefern, und das LLM kann über korrekte Chunks halluzinieren. Nur Agentic RAG (iteratives Retrieval mit Qualitätsprüfung) ist genuin agentisch. HYBRID
Memory Persistenz über einzelne Interaktionen hinaus. Drei Typen: Episodisch (Logs vergangener Interaktionen), Semantisch (Fakten, Regeln — in Vektor-DBs, KGs, oder strukturierten DBs), Prozedural (gelernte Handlungsmuster, z.B. „so habe ich dieses Problem zuletzt gelöst"). Die Originalgrafik reduziert auf „Short-term = Context, Long-term = Vektor-DB". Das ist zu eng: Knowledge Graphs, SQL-Datenbanken, episodische Logs sind gleichwertige Persistenzformen. Prozedurale Memory (der Agent merkt sich wie, nicht nur was) fehlt fast überall. HYBRID
Grounding Verankerung von Agentenaussagen an verifizierbaren externen Quellen. Methoden: Zitierung mit Quellenangabe, Faktencheck gegen strukturierte Daten, Tool-Aufrufe zur Verifikation. Das Originalbild verwechselt zwei Dinge: Grounding im NLP-Sinn (Sprache ↔ Weltwissen) und Grounding als Faktenverifizierung. Zudem: Wer entscheidet, was eine „trusted source" ist? Diese Meta-Frage ist selbst ungelöst und politisch aufgeladen. NICHT AG.
04 Steuerung & Sicherheit — Wie wird der Agent kontrolliert?

Mechanismen, die verhindern, dass autonome Agenten Schaden anrichten — vom Leitplanken-System bis zur menschlichen Aufsicht.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
Guardrails Sicherheitsgrenzen auf drei Ebenen: Input-Guardrails (Prompt Injection Detection, Content-Filter), Execution-Guardrails (Tool-Whitelisting, Rate Limits), Output-Guardrails (Compliance-Checks, PII-Redaktion). Das Originalbild nennt nur „safety boundaries" ohne Differenzierung. Kritisch: LLM-basierte Guardrails sind selbst durch Prompt Injection angreifbar. Robuste Systeme brauchen nicht-LLM-basierte Guardrails (Regex, Classifier, deterministische Regeln) als äußere Schicht. HYBRID
Sandboxing Isolation der Agentenausführung von Produktivsystemen. Betrifft nicht nur Code-Ausführung, sondern auch API-Calls (Sandbox-Endpoints), Datenzugriff (Read-only-Modi), State-Isolation (Agent kann Produktions-State nicht mutieren). Das Originalbild verengt auf „run code safely". Produktive Sandboxes sind mehrdimensional: Netzwerk-Isolation, Dateisystem-Isolation, API-Scope-Limitation, Budget-Caps. Container (Docker) allein sind kein Sandbox — der Agent braucht auch eingeschränkte Credentials. HYBRID
Human-in-the-Loop Menschliche Intervention im Agenten-Workflow. Drei Modi: Approval Gate (binär: ja/nein vor kritischen Aktionen), Steering (Mensch gibt neue Richtung vor), Escalation (Agent eskaliert bei Unsicherheit an Menschen). Die Originalgrafik kennt nur den Approval-Modus. In der Praxis ist Steering (Mensch korrigiert Kurs mid-flight) oft wichtiger. Auch: HITL skaliert nicht — bei 1000 Agentenläufen pro Stunde kann kein Mensch jede Approval-Anfrage prüfen. Risiko-basiertes HITL (nur bei hoher Unsicherheit) ist die Praxis. AGENTISCH
Reflection Der Agent evaluiert sein eigenes Output und revidiert bei erkannten Fehlern. Varianten: Self-Critique (Agent bewertet sich selbst), Verification (Agent prüft Output gegen Spec), Multi-Perspective (verschiedene Prompts bewerten dasselbe Ergebnis). Fundamentales Problem: Reflection ist nur so gut wie die Evaluationsfähigkeit des Modells. Ein Modell, das seinen eigenen Fehler nicht erkennt, „reflektiert" im Kreis. Multi-Perspective Reflection (z.B. vier unabhängige LLM-Passes wie in der SDD Phase 2) ist deutlich robuster als Single-Pass Self-Critique. AGENTISCH
Error Recovery ERGÄNZT Strategien für den Umgang mit Fehlern zur Laufzeit: Retry mit Backoff, Fallback auf alternatives Tool/Modell, Graceful Degradation (reduziertes Ergebnis statt Totalausfall), Checkpoint/Resume. Fehlt in fast allen populären Übersichten, ist aber in der Produktion das Konzept mit dem höchsten ROI. Ohne Error Recovery ist jeder Agent fragil. LangGraph bietet Checkpointing; die meisten Frameworks ignorieren das Thema. AGENTISCH
Trust Chains & Confused Deputy ERGÄNZT In Multi-Agent-Systemen: Wenn Agent A Agent B eine Aufgabe delegiert, handelt B mit den Berechtigungen von A. Wird B manipuliert (z.B. via Prompt Injection in einem Dokument), kann B die Berechtigungen von A missbrauchen — das Confused-Deputy-Problem. Das größte ungelöste Sicherheitsproblem in agentic AI. Die Originalgrafik nennt Guardrails und Sandboxing, aber nicht die transitive Vertrauenskette, die beide unterminieren kann. Jeder Agent mit Tool-Zugriff und Input aus nicht-vertrauenswürdigen Quellen ist potenziell betroffen. AGENTISCH
05 Betrieb & Qualität — Wie weiß man, ob der Agent funktioniert?

Evaluation, Monitoring, Observability — die Konzepte, die in der Produktion den Unterschied zwischen Demo und Deployment machen.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
Evaluation (Evals) Systematisches Testen von Agentenverhalten. Dimensionen: End-to-End (Ergebnis korrekt?) vs. Step-Level (jeder Schritt sinnvoll?). Methoden: deterministische Checks, LLM-as-Judge, Human Eval. Offline (vor Deployment) vs. Online (in Produktion). Das Originalbild suggeriert, Evals seien gelöst („test whether an agent performs correctly"). Tatsächlich ist Agent-Evaluation ein offenes Forschungsproblem: Welche Metrik? Wie reproduzierbar? Wie bewertet man Zwischenschritte, wenn nur das Endergebnis zählt? HYBRID
Observability ERGÄNZT Laufzeit-Transparenz: Traces (welche Schritte hat der Agent gemacht?), Logs (was hat er „gedacht"?), Metriken (Latenz, Token-Verbrauch, Fehlerrate pro Schritt). Tools: LangSmith, Arize Phoenix, Braintrust u.a. Fehlt komplett in der Originalgrafik. Ohne Observability ist jeder Agent eine Black Box. In der Produktion ist „der Agent hat das falsche Ergebnis geliefert" nutzlos — man braucht: „In Schritt 3 hat er Tool X mit Parametern Y aufgerufen und Ergebnis Z bekommen, woraufhin er fälschlich zu Schritt 5 gesprungen ist." AGENTISCH
06 Integration & Konfiguration — Wie wird der Agent angebunden und eingestellt?

Schnittstellen-Protokolle und Konfigurationskonzepte — wichtig, aber nicht genuin agentisch.

KonzeptDefinition & AbgrenzungKritische AnmerkungenStatus
MCP / Tool-Protokolle Standardisierte Schnittstellen zwischen Agent und Tools. MCP (Anthropic) ist ein Vorschlag, nicht der einzige: OpenAI Function Calling, Google Genkit, LangChain Tool-Interface sind Alternativen. Alle lösen dasselbe Problem: Wie beschreibt ein Tool seine Fähigkeiten maschinenlesbar? Das Originalbild nennt MCP „the universal connector" — das ist Marketing, kein Fakt. MCP hat gute Verbreitung, aber kein De-facto-Monopol. Die Wahl des Protokolls ist eine Infrastrukturentscheidung, kein agentisches Konzept. NICHT AG.
Agent Persona / System Prompt Instruktionen, die Ton, Verhalten und Grenzen des Agenten definieren. Auch bei nicht-agentischen LLM-Anwendungen Standard. Abgrenzung: Konfiguration, kein Architekturmuster. Die Aufnahme als „agentic concept" im Original ist kategorial falsch. Jeder Chatbot hat eine System Prompt. Was bei Agenten spezifisch wird: Persona muss über viele autonome Schritte stabil bleiben — das erfordert Reinforcement durch Wiederholung oder strukturelle Maßnahmen (z.B. Persona in jedem Sub-Prompt). NICHT AG.
